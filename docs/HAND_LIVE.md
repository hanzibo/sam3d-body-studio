# Gemini 336L 手部实时流

重启 Studio，进入 **手部实验 → ⑥ 相机实时**。此功能沿用独立手部路径，不经过身体解码器；RGB 与实际相机内参参与推理，深度不参与拟合。检测器为 WiLoR 专用左右手 YOLOv8m-Pose，最多保留左、右各一只手。

## 操作

1. 上方选择“采用 512 加速方案”（FP16）或“试用 INT8 512”（实验）。默认勾选“加载后自动离线预热”，检查旁边的本地样本路径。
2. 点击“应用并加载 / 预热”。后台加载模型、检测器，用已有照片完成 B1/B2 预热；此时无需连接相机或摆手。看到“离线预热完成”后继续。
3. 点击“打开相机预览”，保持整只手和少量手腕入画。原来的预热按钮现为“在线补充预热（可选）”，正常情况下无需点击。
4. 选择“原图叠加”或“三维场景”，直接点击“开始实时重建”。左侧是最新 RGB；右侧使用该次推理对应的 RGB，避免与更新的预览错位。
5. “停止实时重建”保留最后画面和模型，等待当前帧完成后可切换显示方式并重新开始。“关闭相机”释放设备；底部“释放 / 取消”同时停止推理并释放模型。

## 已接入的加速选项

实时、照片和离线序列共享同一个 HandExecution 配置及工作进程，不另建未经验证的加速实现：

| 选项 | 实时链路行为 |
| --- | --- |
| FP16 / INT8 编码器 | 均为 512；FP16 可批量编码，INT8 B2 顺序执行两次静态 B1 编码再共用双手解码 |
| 检测器 TensorRT FP16 | 每个实际处理帧都重新检测，不沿用旧框；也可保留原生检测器作基线 |
| 解码器编译 | 沿用 torch.compile，单/双手分别预热 |
| MHR 前处理编译 + CUDA Graph | 保持 FP32；动态批量分别捕获 |
| 反馈复制优化 | 复用重复反馈数据 |
| 中间预测关键点路径 | 中间反馈只计算需要的关键点，保留既有预测次数和姿态修正 |
| 最终手部网格路径 | 直接生成选定手部顶点，避免完整表面生成后截取；骨架仍保留必要完整 FK |

加载后配置锁定。切换精度或编译选项需先释放再加载、预热。身体 384 及其他尚未验证的手部精度选项没有自动移植。

## 自动离线预热

启动方案中可选择预热照片、关闭自动预热；选择保存在本机 QSettings。机器默认照片由 `config/local.json` 的 `hand_warmup_image` 指定，示例配置采用 `assets/hand-warmup.jpg`。此目录的默认样本图片已排除 Git，私人录制照片不随源码发布。本机已配置 Data 盘 Gemini 双手序列的一帧；不会复制或上传原始数据。

预热执行实际手框检测及手部网络。使用样本的相机内参；若没有内参，使用估算内参，仅用于预热。除原始画幅外，额外覆盖 Studio 的 1280×800 相机布局，缩放/填边时同步更新内参。用三次实际执行覆盖出现的批量，再补齐 B1/B2。若只有一只手，允许复制该手裁剪来预热 B2；这只是编译/图捕获输入，不作为双手预测结果。完成后重置跟踪状态，不将样本姿态带到用户画面。

启动报告在“实际配置与任务报告”中显示成功/跳过/失败、样本路径、画幅及耗时。缺失图片、错误内参或未检测到手会明确提示未完成预热，不会伪报成功；模型仍可用于手动任务或在线补充预热。预热过程不导出样本网格，不替换用户当前照片。首次编译和每进程 CUDA Graph 建立依旧耗时，只是前移到加载阶段；未改变模型权重，也不是用样本训练网络。更换相机画幅或输入形状仍可能触发额外首次开销。

`tests/hand_startup_warmup_gui.py` 在相机关闭时加载真实 INT8 512、自动预热，再不经过在线预热直接回放单/双手流。本机验证：加载约 17 s，离线预热约 11.9 s；首个单手/双手帧工作进程约 99 / 146 ms。证据在 `/run/media/hzb/Data/experiments/hand-startup-warmup-20261113/validation.json`。该首帧耗时为录制 RGB 注入结果，不是物理相机到屏幕的完整延迟，也不是所有机器的加载时间保证。

## 调度、互斥和数据

- 与第一页共享 CameraClient 与 SDK 进程；相机选择的实际 RGB 内参直接传入，不依赖照片内参复选框。
- RGB 设备采集 30 FPS，预览默认 15 FPS，手部实时运行期间供帧 30 FPS，停止后恢复 15 FPS；界面 FPS 上限是调度上限，不是速度保证。
- 只允许一个推理请求在途；繁忙期间取最新相机帧。结果提交显示后即可派发下一帧，不再等待窗口交换完成。绘制中的结果不被覆盖，另外最多保留一个等待显示的结果；若显示跟不上，只替换等待项，并记录 `render_dropped`。窗口隐藏或最小化时暂停派发。
- 相机 socket 接收、JSON/Base64 解析和 JPEG 解码均在独立 Qt 线程中进行；线程通过一个最新帧槽位通知 GUI，不逐帧排队发送整幅图像。QImage 发布后只读，窗口及 OpenGL 仍在 GUI 线程操作。原身体实时流继续保留可用的 JPEG 字段。
- MJPG 预览直接传递相机压缩数据，相机进程不再为每帧预览解码 BGR；PNG 拍照及其他像素格式仍按需解码。采集仍用 SDK 独立进程轮询；未将重活搬进 SDK 回调。
- 无手帧清除显示中的旧网格。停止会等待当前请求结束，再删除临时场景；模型异常退出或超时会清理现场。
- 与身体模型、MHR 实验室、SAM3 互斥。实时运行时禁用照片推理、序列任务与相机倒计时拍照；RGB-D 采集需先停止手部流。
- 不保存 RGB、视频或逐帧重建。临时目录只保留覆盖更新的 input.jpg 与 scene.npz；停止后删除。实时 NPZ 仅包含顶点、面、关节、骨架边、内参五项，固定模型信息每段流首次检测到手时发送一次。照片及离线序列仍保留完整原生参数。计时摘要保存 `outputs/hand-streams/*.json`，可在“数据管理”查看/删除。模型会话日志仍在 `outputs/sessions/`。
- 摘要包含请求配置、实际后端信息、检测/重建时间、显示 FPS、P95，以及主机收到帧到 OpenGL frameSwapped 的延迟。该延迟不含曝光及 USB 传输。

## 验证

`tests/test_hand_stream.py` 检查相机内参、输入校验、场景覆盖、流状态重置与 B1/B2 预热。`tests/hand_live_gui.py` 在 Xvfb 中运行真实模型，注入已录制的双手 RGB 流，测试叠加/三维、停止重启、在途取消和实际 Gemini 连接。设置 `HAND_LIVE_FP16=1` 运行 FP16，默认 INT8。

实机若画面内没有手，只能验证采集、内参、检测、无手清除与显示；不能把这种吞吐当作含手重建速度。Xvfb 下软件 OpenGL 与图像注入会影响端到端显示成绩。

## 单手延迟与检测输入优化

实时 TRT 手框检测现默认复用 pinned/GPU 缓冲区并直接处理 RGB，省去整图 RGB/BGR 往返复制；LetterBox 与归一化计算保持一致。实际实现写入检测器元数据。严格配对脚本为 `scripts/benchmark_hand_preprocess.py`，传入 `optimized_preprocess=False` 可使用旧 TRT 预处理进行基准比较。

实时状态下方显示“派发时帧龄 + 工作进程 + 传输/装载 + 等待显示”，状态行悬停可查看更多分项。停止后摘要记录各项均值/P95。帧到显示含取用旧帧的时间；它不等同于检测+重建时间，也不等同于 FPS 的倒数。阶段时间有小量计时与事件调度误差。

摘要新增 `gui_delivery_ms`（解码完成到 GUI 取走最新帧）、`render_queue_ms`（结果等待提交显示）、`paint_cpu_ms`（叠加 draw_frame/draw_pose 的 CPU 调用时间）。最后一项含 OpenGL 驱动调用，未用 GPU query，不等同于 GPU 纯绘制耗时，也不能用它将剩余显示耗时全部归因于 VSync。结果保留真实帧编号，只有对应帧实际执行 paintGL 后的交换才计入叠加显示样本。

注意计时起点变更：旧相机进程在 BGR 解码之后记录 `received_monotonic`；现在 MJPG 在 SDK 彩色帧可用后记录，并随包标注 `receipt_stage=sdk_color_frame_available`。新旧真实相机延迟不能忽略此差别直接比较。录制 socket 回放以发送时刻作为一致的比较起点。

线程与边界回归：`tests/camera_receiver_smoke.py --physical` 检查 GUI 阻塞时后台仍取最新帧、分包、损坏帧恢复、命令、PNG 拍照与实体相机重连；`tests/test_hand_live_scheduling.py` 检查慢显示丢弃等待项、RGB/网格配对、停止等待在途请求及隐藏暂停。`tests/hand_scheduling_benchmark.py` 通过实际本地 socket 回放单手数据，设置 `HAND_BENCH_OUT` 指定 JSON 路径；`HAND_BENCH_PARITY=1` 追加固定 JPEG 的完整/精简输出数组对照。

2026-11-13 同装置单手 socket 回放：改动前 70 帧平均 146.7 ms、8.57 FPS；最终两轮各 70 帧平均 137.2 / 136.7 ms、9.66 / 9.56 FPS。数值对照中顶点最大差异约 5.96e-8，关节、面、边和内参完全一致。38 项 CPU 检查及单/双手 GUI、实体相机生命周期通过。完整证据位于本机 `/run/media/hzb/Data/experiments/hand-scheduling-20261113/REPORT.md`。此为 Xvfb 和录制图像回放的系统性能结果，不能保证真实桌面稳定超过 10 FPS。

验证报告位于本机 `/run/media/hzb/Data/experiments/hand-latency-20261113/REPORT.md`。不要将孤立组件速度或 Xvfb 测试帧率当作所有现场动作的保证。

## 手部预测次数与回调编译（2026-11-13）

在顶部“启动方案设置”先选择“手部中间预测”（0–5次）和“中间预测回调整体编译”，再应用并预热。快捷FP16 / INT8加速方案默认启用编译且保留5次预测；六层解码和最终预测始终保留。加载后选项锁定，需释放模型后修改并重新预热。减少次数可能改变姿态与相机位置，建议从5次开始对照4/3次。

照片、序列、相机实时使用同一常驻模型与选择。实际配置和首次流结果的 `feedback_runtime` 会写入实时摘要，便于确认生效次数。固定框速度与差异见 [手部加速说明](HAND_ACCELERATION.md)，不直接视作相机端到端帧率。

## 自动找手范围与置信度

顶部“启动方案设置”提供共享的“自动找手范围”和“检测置信度”（0.05–0.95，默认0.40），照片自动找手、序列和实时流共用。两项记住上次选择；实时运行时可修改，新请求按新值执行，不重载模型。手动框选仍使用其独立的“手部方向”。

- 双手：使用检测器左右类别及现有短时连续性，每侧最多一只。
- 单手：强制右手 / 强制左手：**忽略YOLO左右分类**，置信度过滤后的全部框作为候选，按用户指定类别重建，最多一只。照片选最高置信度框，连续流还参考短时框连续性。左手使用现有镜像规范化链路。框不存在或低于阈值时清除结果，不凭空制造手框。

检测器原始标签保留为 `raw_side`，用户指定类别为 `forced_side`，最终类别为 `side`，`identity_source` 说明来源。它们保留在照片/序列报告和实时摘要每帧 `detected_hands` 中；`detection_options` 保存阈值与模式。未加入跨类别重叠框强制去重，以免双手真实交叠时被错误删去；单手模式天然最多生成一个模型。

验证包括模拟同位置左右双框、置信度过滤、初帧标签错误和跟踪后的类别翻转；真实Qt+GPU工作进程用录制的单手/双手图像在线切换双手/强制左手/强制右手与阈值，确认下一帧选项传入及1/2模型数量，证据：`/run/media/hzb/Data/experiments/hand-forced-side-20261113/validation.json`。本轮未连接物理相机验证。

### 手部 One Euro 姿态 / 位置滤波（2026-11-13）

手部页启动方案中新增独立的 **One Euro 姿态（手指＋手掌朝向）** 与 **同时滤波位置**。两者默认关闭，便于保留原始基线；当前作用范围是相机实时流，不改变照片或离线序列结果。开关与三项参数通过每次实时请求传给后端，无需重载权重，设置自动记忆。

| 参数 | 初始值 | 调节作用 |
| --- | --- | --- |
| 最小截止频率 Hz | 1.50 | 减小可增强静止平滑，响应延迟会增加 |
| 速度响应 β | 0.50 | 增大可提高运动时的响应，动态滤波会减弱 |
| 导数截止频率 Hz | 1.00 | 平滑速度估计；建议起初保持 1.00 |

建议先仅开姿态，使用 `1.50 / 0.50 / 1.00`；静止仍抖可先把最小截止降为 `0.8`，动作拖尾明显则增大 β。姿态和位置共享三项设置，但内部历史独立；手部潜在系数与角速度的单位不同，相同 β 的数值不能解释为相同强度。

实现位于 `hand_temporal.py`：

- 手指：对网络最终的手部潜在系数向量作 One Euro，再走原有手部系数→MHR 姿态的映射。
- 手掌朝向：按 SO(3) 最短旋转差计算角速度，以自适应截止频率作旋转插值，不逐元素平滑旋转矩阵或欧拉角。
- 可选位置：平滑规范右手坐标中的 `pred_cam_t`，再按已有约定恢复左手镜像。位置保持关闭时，原始相机平移保持不变。
- 编码器与解码器仍各运行原来的一次。姿态开启后，额外运行一次最终 MHR，复用手部紧凑网格 / 编译 / CUDA Graph 路径；网格、关节和旋转一致，随后重新投影。不把滤波结果反馈到下一帧网络，也不修改中间预测。
- 体型、尺度等其他参数仍取当前帧网络输出，因此滤波不能保证消除所有外形抖动，也不能修复错误识别。滤波是因果的，会引入响应滞后；β 不等于延迟毫秒数。
- 左右手各有独立历史。新流、输入内参/尺寸或强制侧变化、调参、关闭滤波、缺失、时间戳非递增、间隔超过 0.5 秒、大幅框位置跳变及推理异常都会清除相应历史。
- 自动离线预热会同时覆盖可选滤波后的最终 MHR 输入签名，并在完成后清空滤波状态；不需要把在线摆手作为预热条件。若禁用离线预热，首次开启可能遇到额外编译。

实时 `scene.npz` 中渲染数组是当前选用结果；开启滤波时另保留每侧 `*_raw_vertices / *_raw_joints / *_raw_global_rotations / *_raw_camera_translation` 和原始手部参数。该文件仍是单文件覆盖的临时结果，不会自动保存整段网格历史。实时会话 summary 每帧保存 `one_euro` 配置、历史帧数和处理时间；状态栏显示额外滤波耗时，不把它隐藏在原有“重建”指标中。

验证：`tests/test_hand_temporal.py` 检查静止噪声抑制、跨 ±180° 最短旋转、有效旋转矩阵、左右独立历史、断流/换参/跳框重置和原始数组不变。`tests/hand_temporal_integration.py` 在 RTX 4060、INT8 512、3 次中间预测、其他已验证加速全部开启的配置下检查真实 MHR / 关节 / 投影 / 原始输出保留。已有录制数据的连续 25 帧、固定代表手框测试（丢弃前 5 帧计时）：

| 数据 | 滤波＋额外 MHR 均值 / P95 | 完整手部重建均值（不含检测/显示） | 腕部对齐关节帧间变化：原始→滤波 |
| --- | --- | --- | --- |
| 单手 | 4.64 / 5.79 ms | 72.21 ms | 2.74 → 1.37 mm |
| 双手 | 4.89 / 5.13 ms | 119.15 ms | 3.92 → 1.65 mm |

这些帧间变化包含真实动作，不是静态抖动真值或精度评测，不能据此声称提高重建精度。样本时间间隔按 15 Hz 送入滤波器，额外耗时包含参数滤波、传输、MHR 和回传；不代表物理相机端到端延迟。结果位于 `/run/media/hzb/Data/experiments/hand-one-euro-20261113/validation.json`。
