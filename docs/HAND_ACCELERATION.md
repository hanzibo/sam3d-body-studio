# 手部 512 加速方案

本页加速独立手部分支，不修改身体页的四种启动方案，也不修改上游源码。入口是 Studio → 手部实验；加载前可点“采用 512 加速方案”，或逐项选择，随后预加载、预热。恢复基线按钮恢复原生编码器、原生手框检测、关闭编译与图回放。加载期间配置锁定，换方案须先释放模型。

## 2026-11-13：回调编译与预测次数

手部页“启动方案设置”新增两项，须在加载前选择：

- **中间预测回调整体编译**：覆盖姿态/相机参数预测、几何输出坐标转换、相机投影与裁剪坐标转换。实际是 MHR Graph 前后的两个 `fullgraph=True` 编译区；MHR 参数转换与图回放沿用现有实现。直接把含 Graph/NumPy 的 Python 回调整体包进 `torch.compile` 会断图甚至变慢，因此未采用单个大包装。静态 faces 只在加载时转成 NumPy。
- **手部中间预测**：0–5 次，N 次对应层 `0..N-1` 后执行预测及反馈；六层解码和第六层后的最终预测始终执行。0 次仍会进行最终预测。减少次数改变反馈条件，可能改变姿态和相机位置，属于实验配置。

FP16 / INT8 快捷加速方案启用回调编译，默认仍保留 **5 次**。恢复原生基线关闭编译并恢复 5 次。加载后两项锁定，释放模型后才能修改；离线预热、照片、双手序列与实时相机共用同一配置。启动状态、逐手 report.json 与序列启动配置记录实际选择，`feedback_runtime.last` 记录实际关键点/表面调用及反馈次数。

本机 FP16 TRT 512、FP32 解码器/MHR，已有 4 个代表帧（2 单手、2 双手），各方案预热 4 次，正反顺序交替各 20 次。固定手框重建平均耗时如下，**包含裁剪/H2D/网络/MHR/同步，不含检测、D2H、导出和渲染**：

| 配置 | 单手 ms | 双手 ms |
|---|---:|---:|
| 上一版，5 次 | 95.32 | 155.18 |
| 回调编译，5 次 | 88.85 | 148.35 |
| 回调编译，4 次 | 84.99 | 145.55 |
| 回调编译，3 次 | 81.68 | 141.33 |
| 回调编译，2 次 | 78.25 | 138.30 |
| 回调编译，1 次 | 74.73 | 134.27 |
| 回调编译，0 次 | 70.77 | 130.44 |

5 次编译相对基线的相机系顶点最大差小于 **0.001 mm**，投影最大差小于 **0.001 px**。减少次数没有等价性保证，例如 3 次时代表帧相机系顶点最大差达到约 **53.6 mm**；局部关节和相机位置差应分开看。所有差异均相对同帧五次预测结果，没有三维真值，不能当作真实精度误差。建议先保持 5 次，再自行对照 4/3 次。

INT8 / FP16 混合编码器也已补测两个代表帧（单手、双手，各20次交替）：5次基线为 **79.76 / 127.91 ms**，5次编译为 **72.94 / 118.98 ms**，3次编译为 **65.63 / 110.69 ms**；五次编译相机系顶点最大差小于0.001mm。原始结果在同实验目录的 `int8/paired.json`。

真实 Qt + 隔离工作进程验证：INT8、3次预测，先自动离线预热B1/B2及1280×720、1280×800，再注入已有单手/双手RGB帧完成彩色叠加连续显示。断言GUI启动配置、工作进程实际三次反馈和一次最终手表面调用一致；相机未打开，不将录制帧回放当作本轮物理相机验证。证据在 `gui-int8-3/validation.json`。

入口：`scripts/benchmark_hand_callbacks.py`；默认 FP16，也支持 `--backbone trt_int8`。原始计时、输出数组和分项差异在 `/run/media/hzb/Data/experiments/hand-callback-20261113/fp16/paired.json`。CPU 调度测试与上游五次路径精确对照；Qt 配置与锁定测试在 `tests/hand_callback_controls_gui.py`。

## 已接入的执行项

| 选项 | 执行内容 |
|---|---|
| TensorRT FP16 · 512 编码器 | 复用已登记并验证哈希的 `backbone_engine_512`。按实际 IO 类型和动态批量配置分配缓冲区，支持单手与双手；双手分开裁剪为 B=2，保持一个 hand 前向。 |
| 解码层编译 | `torch.compile` 编译 hand decoder 的各层，按所选次数保留中间反馈、参数预测及手部姿态修正。层内 fullgraph=True；不编译整个 GUI 或 Python 任务循环。 |
| MHR 前后处理编译 | 编译原生 hand head 的 `mhr_forward` 参数组装、转换和输出处理，允许图中断；不声称原始 TorchScript MHR 整体转成 Inductor。 |
| MHR CUDA Graph | 对几何计算回放，按 B=1/B=2 分开缓存静态输入，并复制返回值避免后续调用覆盖。保留原有姿态修正。 |
| 自动手框 TensorRT FP16 · 640 | 可选、单独构建的 WiLoR YOLOv8m-Pose 专用手检测器，提取框/左右标签，不输入其 21 点到 SAM。 |
| 反馈复制优化 | 将 2D/3D 反馈合并为各一次 token/augment 复制，并在启用解码编译时编译反馈计算。仅按本次调用的同一姿态对象缓存，不跨帧复用；当前手部每层预测不同，缓存命中为 0。 |
| 中间预测仅计算手部关键点 | 默认 5 次中间预测时保持全部 6 次预测、5 次反馈；依据加载权重的非零依赖构造精确支持集。当前右手 21 点只依赖骨架、不依赖表面顶点，因此中间 5 次跳过完整蒙皮/表面姿态修正和全顶点投影，最后一次根据“最终仅生成手部网格”开关选择完整表面或手部表面，均保留姿态修正。 |

推荐编译模式 default。reduce-overhead 已实测可以运行，但代表帧未见稳定额外收益，且会增加 CUDA Graph 分区/缓存工作。

编码器使用 FP16 计算；手部解码器、MHR 张量与权重保持 FP32。实验 CLI 支持 TF32（FP32 张量、降低矩阵乘法精度），本轮未见稳定收益，因此 GUI 不提供它为推荐开关。相机投影在该实验中保持完整 FP32。

## MHR 图捕获为何需要适配

原始序列化姿态修正里存在临时 CPU→CUDA 分配，并在每次前向构建稀疏矩阵，不能直接进行 CUDA Graph 捕获。自有适配层使用相同 MHR 权重、相同完整骨架、相同蒙皮及姿态修正；将旋转特征构造放在设备端，将固定稀疏首层权重一次性展开为稠密矩阵。没有关闭 correctives，没有修改权重或减少反馈次数。

每种批量首次图捕获前，使用同一输入将适配模块与原始 TorchScript 输出进行 assert_close 校验（rtol=1e-5，atol=1e-3，MHR 内部厘米单位），记录最大顶点差 `mhr_graph_parity_mm`。不满足即报错，不静默跳过或退回一个不同方案。后续跨姿态对照仍需要通过实验验证，不把首帧校验视为完整精度证明。

关键点专用路径单独做首次批量校验（rtol=1e-5，atol=1e-6 米），记录 `intermediate_parity_mm` 和实际支持集。它保持全部 127 节点的参数映射及 FK，不手动挑选少量骨架以免丢失父节点依赖。若映射含表面支持，则保留这些顶点的形状、表情、姿态修正和蒙皮计算。每次返回独立数据，避免后续 Graph 回放覆盖之前层的反馈。控制器在异常和正常返回后都清理中间状态；最终输出默认走完整 MHR；开启“最终仅生成手部网格”后使用相同参数和骨架，裁剪形状基、表情基、姿态修正末层输出行与蒙皮影响列表，只生成 2321 个手部顶点。完整 127 节点 FK 和姿态修正隐藏层保留。

“采用 512 加速方案”选中反馈优化、中间关键点和最终手部网格三项。关闭最终手部网格即可对照上一轮反馈/关键点方案；再关闭前两项可复现此前 TRT512 配置。“恢复原生基线”关闭所有项。

原生 hand head 还会投影并不用于手部显示的整个人体表面。若某个无关顶点恰好位于相机平面，透视除法可能产生非有限坐标。验证仍拒绝任何无效的 3D/相机参数、手部投影，或离开相机平面的异常投影；只允许距相机平面不超过 1e-6 米的非手部顶点投影无定义。原始投影保留，`pred_keypoints_2d_verts_valid` 标记有效性，报告记录 `undefined_nonhand_projection_ids`，不编造像素坐标。首次完整测试的中止记录及单帧排查日志保留，正式计时使用独立重跑目录。

## 预热与缓存

- 权重加载完成后，首次预热会触发 torch.compile 和 CUDA Graph 捕获；原生单手、双手批量需要分别预热。
- 自动双手预热发现两只手时，会同时补充单手批量预热，降低手进出画面时首次切换的卡顿。
- TensorRT 引擎为现有磁盘文件，启动直接加载；不自动重新转换。模型编译缓存保存在配置的 `inductor_cache`（当前为 Data 盘）。CUDA Graph 的静态输入/输出缓存属于当前进程，释放模型后需重新捕获。
- 所有手部作业沿用独占 GPU 租约及 7 GiB RAM / 2 GiB swap 工作进程限制。模型不与身体 / SAM3 工作进程同时常驻。

## 权重、引擎与输出

`config/local.json` 可配置：

- `backbone_engine_512`：既有 512 编码器引擎，不复制第二份。
- `hand_detector_checkpoint`：原有 WiLoR detector.pt。
- `hand_detector_engine`：独立手部检测器引擎，当前 `/run/media/hzb/Data/models/sam3d-hands/detector/detector_fp16.engine`。
- `hand_sequence_outputs`：GUI 新任务保存目录。

本机构建检测器脚本为 `scripts/build_hand_detector.py`，应在限内存 systemd scope 中使用 Fast 环境运行。仅写入指定目录的副本/ONNX/engine，不覆盖原始 WiLoR 权重；登记完成后仍须对新 GPU/TensorRT 环境重新核验。权重及引擎不随源码分发。

每次手部报告保存 execution 选项、引擎哈希/IO 信息、MHR 校验差异及嵌套计时；序列 sequence.json 也保存启动配置。默认路径仍可回退至原生方案。

## 验证入口

- `scripts/benchmark_hand_execution.py`：原生、仅 TRT、解码层编译、MHR 编译/Graph、组合、TF32、reduce-overhead 的固定手框对照。
- `scripts/benchmark_hand_detector.py`：原生/引擎手框的实际端到端检测计时及框重合度。原生自动矩形 letterbox 与 TRT 固定 640 正方形 padding 不完全一致，检测框可能改变，不将这一变化归因于 SAM 数值误差。
- `tests/hand_automatic_gui.py`：通过 HAND_GUI_EXECUTION JSON 环境变量测试指定启动配置，真实加载 GPU、检测、预热、双手重建、短序列、视频及回放，不操作用户桌面。
- `scripts/profile_hand_decoder.py`：按层、姿态回调、MHR、投影和反馈记录嵌套 CUDA 区间，计时含 CPU 派发间隙，不能直接相加成纯 kernel 时间。
- `scripts/benchmark_hand_feedback.py`：同进程交替 baseline / 反馈优化 / 关键点路径 / 两项组合，记录网格、关节、旋转、MHR 参数和投影差异。
- `scripts/report_hand_feedback.py`：组合固定框消融、完整序列计时及数值对照。第二轮报告在 `/run/media/hzb/Data/experiments/hand-feedback-20261112/REPORT.md`，上一轮结果保留。

实测报告及原始数据：`/run/media/hzb/Data/experiments/hand-acceleration-20261112/`。速度必须区分固定手框网络计时、含检测的推理、含压缩读写的离线吞吐及 GUI/视频渲染，不将 MP4 的 30 FPS 当作推理帧率。没有手部三维真值，数值接近只说明与基线输出接近。

## 最终手部表面专用路径

`final_hand_vertices` 默认 false，GUI 加速预设启用。它保留完整 127 节点 FK，直接计算 2321 个手部顶点及 4613 个三角形，不生成其他部位表面后再截取。形状、表情、姿态修正首层共享原始权重，仅将姿态修正末层的 55317 输出行选为 6963 行，蒙皮影响列表按相同顶点同步裁剪。未量化 MHR，也未减少六次姿态预测。

每个批量首次运行与完整 TorchScript MHR 比较顶点、关键点和骨架状态；CUDA Graph 捕获后每次返回独立张量。报告含 `raw_vertex_layout`、`final_surface_parity_mm` 以及 `feedback_runtime.last.compact_surface_calls`。预热/首次校验会调用完整 MHR，稳定推理的最后一次仅走紧凑表面路径。

启用后 raw NPZ 的 `pred_vertices` / `pred_keypoints_2d_verts` 由 18439 行变为 2321 行，`pred_vertex_ids` 提供对应原始 MHR 顶点编号。导出的显示网格、相机坐标、关节和旋转格式不变。下游不要把 raw 顶点数组行号直接当作完整 MHR 顶点编号。

验证脚本 `scripts/benchmark_hand_surface.py` 在同进程交替测试已有反馈/关键点优化方案与最终手部表面方案，固定手框，覆盖单手、双手和原生无关顶点投影无定义的回归帧。结果位于 `/run/media/hzb/Data/experiments/hand-surface-20261112/`。

## INT8 512 编码器（实验方案）

加载前点击“试用 INT8 512”，或在已选 512 加速配置后从编码器下拉选择 TensorRT INT8 / FP16。`backbone='trt_int8'` 复用已配置并登记哈希的 `backbone_engine_int8_512`，不下载、不重建、不覆盖已有 FP16 引擎。它是 Embedl 混合 INT8/FP16 编码器，IO 为 FP16，手部解码器与 MHR 继续 FP32；并非整个手部模型均为 INT8。

现有 INT8 512 引擎固定输入 `[1,3,512,512]`、输出 `[1,1280,32,32]`。双手时分别执行 B1 编码两次，然后合为 B2 特征送同一手部解码器；六次预测、五次反馈和最终手部专用表面路径均保留。`execution_counts.backbone=1` 是逻辑模块调用次数；每帧 `backbone_engine_executions` 才是实际 TRT 次数（单手 1 / 双手 2）。`backbone_runtime` 记录精度、实际 profile、策略、哈希和累计执行次数。

“采用 512 加速方案”保留 FP16；“试用 INT8 512”启用同样的编译、Graph、反馈、关键点及最终手部网格开关，仅改变编码器。所有选项在加载后锁定，切换前先释放并重新预热。

验证脚本：`scripts/benchmark_hand_int8.py` 同进程固定手框交替计时；`scripts/compare_hand_int8.py` 比较网格、关节、旋转及连续变化代理；`scripts/make_hand_int8_video.py` 生成并排视频；`scripts/report_hand_int8.py` 汇总结果。报告在 `/run/media/hzb/Data/experiments/hand-int8-20261112/REPORT.md`。

此方案会改变预测。没有手部三维真值，需把相对 FP16 的顶点/关节/投影差异和真实精度区分；二阶差分包含真实动作，仅是相对稳定性代理，不是抖动真值。当前 FP16 方案及原始数据完整保留，INT8 作为实验可选项。权重及引擎沿用单独取得资产的授权条款，不随源码分发；见 Embedl 实验文档与许可证审查说明。
